    weir 设计稿

    2026-10-25 · 依据多轮原型的结论 · 原型代码在同目录的 prototype/，属于一次性代码

    weir 是一个跑在你本机的 daemon。它把多个 source 的消息同步进一个 SQLite 文件，按 conversation 聚合。然后它调用你自己配置的 AI，把 conversation 分进 bucket，写好摘要。你在 localhost 的 Web UI 里看，你的 agent 通过 weir-axi 查。

    weir 只读。它不会改 Gmail、Outlook 或 Teams 里的任何状态。已读、完成、静音都只记在本地。

    整个设计靠一个想法成立：sync 和 enrich 分开跑。「打开就是最新」由 sync 保证，新消息一进来就能看到、能搜到。AI 的结果稍后异步补上。AI 慢一点或贵一点，都不影响主体验。

    01weir 负责同步、聚合和分拣，不负责回复

    weir 要解决的是「想知道，但不用动」的那一层信息。比如别人的 PR 合了、某个群在讨论架构、build 挂了但不归你管。逐封点开太累，全部忽略又怕错过。weir 把它们收进一个地方，用你读得快的语言给出摘要，读完一键让它离开视线。

    它是个人工具，也是开放的。AI 和 source 都由用户自己接入，weir 不绑定任何一家。

    术语含义

    plugin实现 source 接口的代码，比如 imap。同一个 plugin 可以配置成多个 source。
    streamsource 里的一路数据，比如一个 IMAP 文件夹，或者以后 Teams 的一个频道。

    conversationweir 判断的「同一件事」。可以跨 thread，以后也可以跨 source。是 UI 和 AI 处理的基本单位。

    ruleconfig 里的确定性匹配规则。开新 conversation 时，它可以直接定下 bucket，也可以让这个 conversation 完全不经过 AI。
    enricherdaemon 里调用 AI 的部分。它分 bucket，写 summary、update、points 和 gist。
    AI profileconfig 里一个有名字的 AI CLI 命令。bucket 按名字引用它。
    gist单条 item 的一句话摘要，说明这条消息带来了什么。
    updateconversation 最近一批新 item 的一句话摘要。UI 上叫「自你上次查看」。
    pointsconversation 的要点，最多 5 条，分为 ask、decision、date、info 四类。
    seqitem 写进数据库的顺序号，全局递增。已读和完成都用它当水位线。
    dirtyconversation 里有 enricher 还没处理的 item，也就是 last_seq > enriched_seq，而且不是 skip_ai。由字段算出，不单独存。
    provisionalsync 为新 thread 开的、没有命中 rule 的 conversation，AI 还没看过。只有它可能被并进别的 conversation。

    02一封新回复从进来到被你清掉，一共经过八步

    本节跟一个具体例子走完全程，后面各节都会引用它。假设如下：你配置了 IMAP source personal-mail。conversation「Northwind 迁移与验收」已经在 action bucket 里，这个 bucket 是 AI 定的。你昨天看完后点了「完成」。今天 14:03，客户回了一封邮件。

    1. sync 拉到这封邮件。scheduler 每 5 分钟调用一次 plugin 的 sync(stream, cursor)，间隔由 sync_every 决定。plugin 返回一条 item，thread_id 是 References 链的根，container_id 是 INBOX。core 按 (stream_id, external_id) upsert，重复 sync 不会产生重复 item。新 item 拿到一个 seq，同时记下 synced_at。core 去掉引用历史和签名，结果写进 body_new，FTS index 同时更新。从这一刻起，UI 和 weir-axi search 都能搜到它。
    2. 按 thread_id 挂进已有 conversation。同一个 thread 的上一条 item 属于「Northwind 迁移与验收」，新 item 跟过去，记为 assigned_by = "thread"。rule 不执行，因为 rule 只对开新 conversation 的 item 生效。这一步不调用 AI。
    3. conversation 立刻重新出现。conversation 的 last_seq 变成新 item 的 seq，比昨天「完成」记下的 cleared_seq 大。所以它回到 action 里，状态是未读。灵动岛那句话里的计数加一，标签页标题变成 (1) weir。这一步没有后台任务，是查询时算出来的。此时 summary 还是旧的。
    4. conversation 变脏，等它安静下来。last_seq 大于 enriched_seq，conversation 就是 dirty。enricher 等它 2 分钟没有新 item 再处理，最长等 10 分钟。客户连发三封，也只处理一次。
    5. enricher 增量更新。它不是 provisional，所以跳过合并判断。enricher 把它和其他 dirty conversation 攒成一批，调用一次 AI CLI。输入是上一版 summary，加上 enriched_seq 之后的新 item。输出是 bucket、title、summary、update、points，以及每条新 item 的 gist。写回后，enriched_seq 前进到这次送出的最大 seq。
    6. AI 重新判断 bucket。bucket_by 是 ai，所以 AI 这次给的 bucket 会写回。客户提了新要求，仍然是 action。如果你手动改过它的 bucket，AI 给的值会被忽略。
    7. 你打开它。阅读区顶部的「自你上次查看」显示 update。下面的对话流从「上次读到这里」开始，每个气泡是一条 gist。想核对英文原文，点 dock 上的「原文」。打开就算已读，seen_seq 前进到 last_seq。
    8. 你点「完成」。cleared_seq 前进到 last_seq，conversation 离开列表，下一条自动打开。灵动岛里的计数跟着变，没有别的提示，也没有撤销。点错了就去「已清理」里点「恢复」。

    三个变体，各自在不同的步骤分叉：

    • 新开的 thread在第 2 步分叉。没有可跟的 conversation，sync 给它开一个 provisional conversation，放在「未分类」里。enricher 在第 5 步之前先判断它要不要并进别的 conversation。见第 06 节。
    • CI 通知也是新 thread，在第 2 步命中一条 skip_ai rule。它的 conversation 直接进 alerts，标题就用邮件主题，之后永远不调用 AI。
    • agent 查询不经过第 7、8 步。agent 运行 weir-axi，首页显示 action 有 1 个未读。weir-axi conv <id> 读到同样的 summary 和 gist。axi 读取不改变已读状态。

    几条约定：

    • configSchema 用 Standard Schema。plugin 作者可以用 zod、valibot 或 Effect Schema 写。Effect Schema 能否直接导出 Standard Schema，这一点还没核实，搭骨架时第一件事就是确认。
    • daemon 启动和 reload 时，用 configSchema 校验 [source.config]。校验失败的报错里带上出错的 config 路径。
    • cursor 的内容由 plugin 决定，比如 IMAP 的 UIDVALIDITY 和 MODSEQ，或者 Graph 的 delta token。core 只负责保存，不解析。
    • more = true 表示还有下一页，core 立刻用新 cursor 再调一次。这样冷启动拉一万封邮件时，每一页都单独落盘，中途崩溃也能从上一页接着来。
    • bodyNew 是去掉引用历史和签名后的正文。plugin 可以自己算。返回 null 时 core 用通用实现。
    • openLabel 是 dock 上「在 Gmail 中打开」按钮里的来源名。
    • me 列出这个 stream 里代表你的地址或 handle。「直接发给我」「@ 我」靠它判断。
    • plugin 用名字加载。内置的写名字，比如 imap。第三方的放在 ~/.weir/plugins/<name>/。公司内部的 source 可以放在单独的私有仓库，不碰主仓库。
    容易误解的地方 你可能以为 thread_id 就是 conversation。它不是。thread_id 只说明「这几条一定是同一件事」，它是归属的线索。一个 conversation 可以包含几个 thread。区别在于是否由 weir 判断。thread_id 来自 source，conversation 由 weir 决定。同理，Teams 群聊的 chat id 是 container_id，不是 thread_id。一个群里可能同时在聊五件事。

    每条 item 都带 thread_id 和 container_id 两个字段，两者含义固定。thread_id 可以为空，Teams 群聊里的大部分消息就没有。

    kind 在 MVP 里只有 message。日历以后作为 event kind 加入，那时用一次 migration 加上 event_detail 表。

    daemon 或 agent 需要知道的放 SQLite，其他放 localStorage

    判断标准只有一个：daemon 或 agent 需不需要知道这件事。

    • 放 SQLite：已读、完成、静音，手动改过的 bucket 和 item 归属。axi 首页要显示未读数，enricher 不能覆盖你的手动修改，所以它们必须在 daemon 那边。
    • 放 localStorage：主题、上次停在哪个 bucket、阅读区的展开状态。这些只跟浏览器有关。主题在状态视图的 Appearance 里选，见第 09 节。

    localStorage 按 origin 存储，origin 包含端口。端口一变，偏好就丢了。所以端口固定为 9347，也就是 weir 四个字母在九宫格键盘上的位置。

    搜索用 trigram 索引，不到 3 个字的词改用 LIKE

    搜索要同时对中文和英文有效。FTS5 默认的 unicode61 分词器两样都做不到。它把一串连续的汉字当成一个词，「报价」只在单独出现时才搜得到。英文它只按整词匹配，migrat 搜不到 migration。trigram 分词器按 3 个字一组建索引，3 个字及以上的词都能按子串搜对。不到 3 个字的词它一条也搜不到，而两个字的中文词恰恰是最常见的查询。

    所以每个词按长度分开处理。原型数据上测过一次，范围是 301 条 item 的 gist 和 body_new，SQLite 3.54.0，通过 bun:sqlite：

    migrat1101111
    PR245880245

    「实际条数」是对同样两个字段做不分大小写的子串匹配得到的。LIKE 在每个查询上都和它一致。LIKE 要扫全表，每次查询 0.80 ms，trigram 的 MATCH 是 0.022 ms。两个数都是 200 次查询的平均，只跑了一轮。301 条上 LIKE 不慢，但它的耗时随条数增长，所以只给短词用。

    • 索引用 tokenize = 'trigram case_sensitive 0'，不分大小写。
    • 查询按空白切成词。3 个字及以上的词用 MATCH，词放进双引号，不当成 FTS 语法解析。不到 3 个字的词用 text LIKE '%词%'，先转义 % 和 _。字数按字符算，不按字节算。
    • 每个词各查出一组 conversation id，再取交集。也就是所有词都要在同一个 conversation 里出现，但可以出现在不同的消息和不同的字段里。
    • 原文只索引 body_new，不索引引用历史。一条回复不会因为它引用的旧文字而命中。
    • --from、--bucket、--source、--since 和 UI 里的 chip 是普通的 SQL 条件，作用在交集上。
    • 命中的是哪条消息、哪个字段，索引不记。API 只对要显示的结果逐个字段再比一次，用来生成命中行和标记。
    search_fts 的结构，以及为什么只用一张表 
    CREATE VIRTUAL TABLE search_fts USING fts5(
  text,
  conversation_id UNINDEXED,
  item_seq UNINDEXED,
  tokenize = 'trigram case_sensitive 0'

    表里有两种行。

    行item_seqtext 的内容谁来写
    每条 item 一行item 的 seq标题、发件人名字和地址、来源名、body_new、gistsync 写入。enrich 写回 gist 时重写。移动 item 时改 conversation_id。软删除时删掉
    每个 conversation 一行空标题、summary、points 的文字开 conversation 时写入。enrich 写回时重写。conversation 删除时删掉
    • 一张表就够。查询的单位是 conversation，每个词只要一次查询就拿到 conversation id。拆成 item 和 conversation 两张表，每个词就要查两次再合并。
    • text 只有一列。哪个字段命中只在显示结果时才需要，那时 API 会逐个字段重新比较，所以不用每个字段一列。
    • item 单独成行，不把整个 conversation 拼成一行。长群聊来一条新消息，sync 只写这一条的行，不用重写整个 conversation。
    • 不用 external content 表。文字来自 item、party、conversation_item 和 conversation 四张表，external content 只能对着一张表或视图。所以 core 在写这些表的同一个事务里写 search_fts，不用 trigger。代价是文字存了两份。

    水位线用 seq，不用时间

    「完成」如果只记一个时间，之后只有比它新的消息才会让 conversation 重新出现。问题出在晚到的消息。IMAP 可能隔几个小时才同步到一封早上发出的邮件。它的 occurred_at 早于你点「完成」的时间，按时间比较就不会重新出现。

    所以水位线比较的是 seq，也就是写进数据库的顺序。只要是 weir 之后才知道的消息，seq 一定更大。显示时间仍然用 occurred_at。

    06新 item 在 sync 时进 conversation，bucket 由 enricher 稍后补上

    一条新 item 分两段处理。sync 时，core 立刻决定它属于哪个 conversation。这一段不调用 AI，所以新消息马上能看到。enrich 时，AI 再做两件事。一是判断新开的 conversation 该不该并进别的 conversation，二是给 conversation 定 bucket、写摘要。

    sync 时按三条规则开或挂 conversation

    规则按顺序执行，前一条命中就停。

    1. 跟 thread。item 的 thread_id 非空，而且同一 thread 已经有 item 在某个 conversation 里，就跟最新那条走，记为 assigned_by = "thread"。你手动把上一条移走了，后面的回复会跟着移过去。被跟的 conversation 的 bucket 不变，它会变成未读，也会变脏。
    2. rule。其余的 item 都要开一个新 conversation。开之前按 config 里的书写顺序匹配 rule，第一条命中的生效。conversation 的 bucket 取 rule 的值，记为 bucket_by = "rule"，之后 AI 不会改它。它不是 provisional，不会被合并。rule 带 skip_ai = true 时，conversation 记为 skip_ai，标题用 item 的标题，永远不送给 AI。同一 thread 后续的回复跟着它，也不送给 AI。
    3. provisional。rule 也没命中，就开一个 provisional conversation。它没有 bucket，显示在「未分类」里，标题暂时用 item 的标题。

    跟 thread 排在 rule 前面，是为了不让一条 item 改变整个 conversation 的去向。如果每条 item 都先跑 rule，一个 PR thread 里最后来的一封 merged 通知，就会把整个 conversation 拽进 alerts。

    冷启动时，最后一条 item 早于 backfill 窗口的 conversation 也按这三条规则开出来，但开出来时 enriched_seq、seen_seq、cleared_seq 都等于 last_seq，provisional 为 0，也就是当作已处理、已读、已完成。它们不调用 AI，只能被搜到，或者在「已清理」里找到。以后这个 thread 来了新回复，conversation 重新出现。因为没有上一版 summary，enricher 会读全部 item 写一份新的，仍然受每批字符上限和单条正文截断的约束。

    enrich 时先合并，再定 bucket 和摘要

    enricher 每 30 秒检查一次。一个 dirty conversation 满足下面任一条件就可以处理：最后一条 item 的 synced_at 已过 2 分钟，或者最早一条未处理 item 的 synced_at 已过 10 分钟。可以处理的 conversation 攒成一批，先过阶段 1，再过阶段 2。本节的时间和数量都是起始值，没在真实数据上调过。

    阶段 1 是合并。只在这一批里有 provisional conversation 时运行。

    • core 先在本地给每个 provisional conversation 找候选。第一类候选是最近 14 天活跃过的 conversation，不含 provisional、skip_ai 和静音的。它们按同一 container_id、FTS 相似度和参与人重合度打分，取前 8 个。第二类是同一批里的其他 provisional conversation。本地一个候选都找不到的，不送给 AI。
    • 这一步用 [enrich] ai 指定的默认 profile。AI 看到 provisional conversation 的标题和正文开头，以及候选的标题和 summary。它输出一张合并表，比如 {"p2": "c7", "p3": "p2"}。不在表里的保持独立。
    • core 按表移动 item，记为 assigned_by = "ai"。指向另一个 provisional 的，顺着链找到最终目标。成环或者引用了不存在的编号，当作不合并。被移空的 provisional conversation 直接删除。
    • AI 只会把 provisional conversation 并进别处。它不拆分已经处理过的 conversation，也不把两个已经处理过的 conversation 合在一起，所以列表里的 conversation 不会自己重排。
    • 你打开、完成、静音、移动过 item 或者改过 bucket 的 conversation，立刻不再是 provisional。所以你正在读的 conversation 不会在眼前消失。

    阶段 2 是 bucket 和摘要。这一批里所有 dirty conversation 都进阶段 2，包括刚在阶段 1 被并进新 item 的目标。

    • 输入是上一版 summary，加上 enriched_seq 之后的 item。没有上一版 summary 时，送全部 item。细节见第 07 节。
    • AI 给每个 conversation 输出一个 bucket。bucket_by 为空或者是 ai 时，core 写回这个值，记为 ai。是 rule 或 user 时，这个值被忽略。
    • AI 给的 bucket id 不在 config 里，就当作没有 bucket，conversation 留在「未分类」，原始输出写进日志。
    • bucket 每次处理都可能变。一个在 fyi 里的 conversation，后来有人在里面直接问你问题，下一次处理就可能变成 action。
    • 写回后，enriched_seq 前进到这次送出的最大 seq，provisional 清零。AI 调用期间又进来的 item，seq 更大，conversation 仍然是 dirty，下一轮再处理。

    一条新邮件在 UI 上的样子

    时间新 thread，没命中 rule新 thread，命中 skip_ai rule回复已有 thread
    sync 之后出现在「未分类」，标题是邮件主题，没有 summary出现在 rule 指定的 bucket，之后不再变化所在 conversation 变成未读，summary 还是旧的
    2 到 10 分钟后被合并的，从「未分类」消失，出现在目标 conversation 里。没被合并的，拿到 bucket、标题和 summary不变summary、update 和 gist 更新，bucket 可能变

    原型在 10 天的 Gmail 数据上测过合并。240 封、192 个 thread，opus-5.5 合并了 6 处，人工看过都合理。gpt-6-luna 合并的 5 处都在这 6 处之内。原型是把所有 thread 一次交给 AI 分组，没有先在本地筛候选，所以这个数字只说明模型分得准，不说明候选筛选的召回率。

    07enricher 增量运行，从不自动全量重算

    enrich 分三个阶段。越往后越贵，所以越往前越要多拦住一些。

    阶段何时运行成本输出
    0. rulesync 开新 conversation 时零bucket。命中 skip_ai 时，整个 conversation 不进 AI
    1. 合并一批里有 provisional conversation 时小，只看标题、正文开头和候选摘要并进哪个 conversation
    2. 摘要conversation 变脏并安静下来之后主要成本bucket、title、summary、update、points、gist

    阶段 2 只读新消息

    • 防抖。conversation 安静 2 分钟才处理，最长等 10 分钟。这两个数是起始值，还没在真实群聊上测过。
    • 增量。输入是上一版 summary，加上 enriched_seq 之后的新 item。没有上一版 summary，或者已经连续增量 5 次，就送全部 item 做一次全量重写，防止 summary 越改越偏。
    • 攒批。多个 dirty conversation 合成一次 CLI 调用，每批最多 max_batch 个 conversation。原型摘要每批 8 个 conversation。生成 gist 时每批最多 30 条 item 或 24000 字符，单条正文截到 1200 字符。
    • 一次调用出全部字段。bucket、summary、points 和 gist 在同一次调用里输出，正文只读一遍。
    • 单条 conversation 不出 gist。只有一条 item 时，gist 和 summary 说的是同一件事。原型 r5 的数据里 189 个 conversation 有 152 个只有一条 item，这 189 个是 gpt-6-luna 聚出的 187 个加上 2 个合成的长 conversation。

    冷启动只 enrich 最近 3 天

    第一次接入一个邮箱，历史邮件可能有上万封。backfill = "3d" 以内的 enrich，更早的只建 FTS index，能搜到但没有摘要。这个窗口可以在 config 里改。

    改了 prompt 或换了模型，旧结果原样保留

    改动只影响之后的处理，不自动重算。手动重算有两个入口：UI 上对单个 conversation 点「重新分析」，或者运行 weir-axi enrich --since 7d。两者都把 enriched_seq 清零，下一轮送全部 item 重写。

    这样做有一个副作用，用户改 prompt 时应该预料到。活跃的 conversation 一来新消息，就按新的 prompt 处理。所以新规则会逐渐覆盖活跃的 conversation，已经安静的旧 conversation 保留旧结果。

    enriched_seq 仍然要保留。它记录 summary 处理到了哪条 item，判断的是「有没有新消息」，和「配置有没有变」无关。

    bucket 可以指定自己的 AI profile

    AI 接口在 config 里是一组有名字的 profile。[enrich] ai 是默认值，每个 bucket 可以用 ai 覆盖。

    这里有一个先后问题。bucket 本身是 AI 分出来的，所以分类只能用默认 profile。分完之后，summary、points 和 gist 才交给 bucket 指定的 profile。

    • bucket 的 profile 和默认的相同时，一次调用输出全部字段。这是常见情况。
    • 两者不同时拆成两次。第一次用默认 profile 只输出 bucket，第二次用 bucket 的 profile 输出其余字段。

    你手动改过 bucket 的 conversation 记为 bucket_by = "user"，enricher 之后不再改它的 bucket。没有这条，你刚改好的分类会在下一条消息进来时被 AI 改回去。

    CLI 约定很窄，任何 agent harness 都能接

    • command 是 argv 数组，不经过 shell 拼接。
    • core 拼好完整的 prompt，从 stdin 传入。prompt 包括系统指令、guide 文件、各 bucket 的 prompt 文件、数据，以及输出 schema。
    • core 取 stdout 里最后一个 JSON 块，用 Schema 校验。这样能兼容在 JSON 前后输出多余文字的 harness。
    • 失败时原始输出写到 ~/.weir/logs/enrich/，重试一次。还失败就保持 dirty，下一轮再试。
    • 数据里的 item 用短编号 m1、m2 引用。原型里模型抄写十六进制 id 时会抄错，换成短编号后就没有这个问题了。

    08bucket 和 conversation 的变更都不触发重算

    找不到的 bucket 一律显示为「未分类」

    conversation.bucket 只存字符串 id。config 里找不到这个 id，UI 就把 conversation 放进「未分类」。「未分类」本来就要有，给还没 enrich 的 provisional conversation 用。所以删除 bucket 不需要写迁移代码。

    「未分类」里的 conversation 有两种来历。一种是 provisional，还没 enrich，列表里这一行带 Sorting 标签。另一种的 bucket id 已经不在 config 里。「未分类」排在所有 bucket 前面，灵动岛、默认标签页、搜索结果的分组都是这样。它有内容时从不隐藏，因为它是 config 还没管到的地方，最需要你看一眼。

    操作结果
    新增 bucket不重算。之后进来的 conversation 才可能落进去。
    调整顺序只影响显示。显示顺序就是 config 里的书写顺序，排在「未分类」后面。没有 priority 字段。
    改 nameid 不变，没有影响。
    改 prompt 或 ai不重算，见第 07 节。
    删除 bucket原来的 conversation 进入「未分类」，等你手动重算或者它们有新消息。
    改 id等于删除再新增。启动或 reload 时，发现有 conversation 引用了 config 里没有的 bucket id，就打一条 warning。

    conversation 只增长，手动操作只有「移动 item」

    • AI 不拆分已经处理过的 conversation，也不把两个已经处理过的 conversation 合在一起。只有 provisional conversation 会被并进别处，见第 06 节。
    • 你可以把选中的 item 移到另一个 conversation，或者移出去新建一个。拆分和合并都用这一个操作完成。手动新建的 conversation 不是 provisional。被移空的 conversation 自动删除。两边的 enriched_seq 都清零，下一轮重新生成 summary。
    • 不提供删除 conversation，用「完成」或「静音」代替。
    • source 那边删了邮件，item 做软删除。summary 等下次有新消息时再更新。

    已读、完成、静音由三个字段推算

    已读按 conversation 算，打开就算已读。「离开视线」用的是原型里的 D1 方案，也就是手动完成。

    stateDiagram-v2
  [*] --> Unread
  Unread --> Read: open
  Read --> Unread: mark unread or new item
  Read --> Done: 完成
  Unread --> Done: 全部清掉
  Done --> Unread: new item
  Done --> Read: 恢复
    状态条件显示在哪里
    静音muted = 1只在「已清理」里。来新消息也不出现。
    已完成last_seq <= cleared_seq只在「已清理」里，可以「恢复」。
    未读last_seq > seen_seq所在 bucket，计入灵动岛那句话的数字。
    已读未完成其余情况所在 bucket，变灰，留到你点「完成」。

    表格从上到下判断，第一条命中的就是当前状态。「重新出现」不需要后台任务。新 item 让 last_seq 变大，查询结果自然就变了。「标为未读」把 seen_seq 设成 last_seq - 1。

    09一个 config.toml 管全部配置，不做设置页

    ~/.weir/
  config.toml
  prompts/          bucket 的 prompt 和 guide，.md
  plugins/          第三方 source plugin
  weir.db
  logs/enrich/      AI 的原始输出

    选 TOML 而不选 YAML。YAML 对缩进敏感，prompt 一缩进错就出问题。它还有隐式类型转换，比如 no 会被解析成 false。Bun 能直接 import TOML。长 prompt 写在单独的 .md 文件里，config 只写路径。

    • guide 是对所有 bucket 生效的额外指令。AI 输出用什么语言，就写在这里，比如「Write titles, summaries and gists in Simplified Chinese」。原型里 gpt-6-luna 有 8 个标题写成了繁体，就靠这类指令约束。
    • bucket 的 name 原样显示在 UI 里，写什么语言都可以。
    • bucket 建议配 3 到 6 个，但没有硬上限。bucket 多了，灵动岛那句话会折行，药丸里的 bucket 区可以横向滚动。
    • 每个 source 一个 [[source]]。plugin 自己的配置放在 [source.config] 里，core 不解析，原样交给 plugin 校验。
    • 以 _cmd 结尾的字段表示「执行这条命令取值」。在 macOS 上可以配合 Keychain，密码不写明文。core 统一处理，plugin 拿到的是取好的值。
    • bucket 的 ai 和 [enrich] ai 只能引用已定义的 profile。拼错了，校验会报出 config 路径。
    • bucket 的 color 可以不写。要写的话，只能从 14 个色名里选：red、blue、green、purple、amber、cyan、pink、lime、sky、orange、teal、indigo、yellow、rose。色名只决定色相，明度和饱和度由 UI 按主题和用途决定，这样对比度由 UI 统一负责，不交给用户。写了不在列表里的名字，校验会报出 config 路径。
    • 没写 color 的 bucket 由 id 算出颜色。先让写了 color 的 bucket 占住各自的色，再按 config 顺序处理其余 bucket：对 id 做 FNV-1a 32 位哈希，模 14 得到起点，沿上面的色名顺序往后找第一个没被占的色。这个顺序里相邻两色的色相大多相差 95 度以上，所以撞色后换到的色也容易区分。bucket 总数不超过 14 个、也没有两个 bucket 写同一个 color 时，不会重色。超过 14 个时允许重色，两个 bucket 写了同一个 color 也就是同色，校验不拦。颜色只跟 id 走，改 name 不会变色。增删或调整别的 bucket 后，原本就拿到自己起点色的 bucket，只要起点色没被显式色或排在它前面的 bucket 占走，颜色就不变。其余 bucket 可能换色，而且可能顺着色名顺序连锁挤动后面几个。Unsorted 永远是中性灰。上面例子里 feed 和 alerts 没写颜色，就走这条规则。

    改了 config 要手动 reload

    daemon 只在启动和 reload 时读取 config.toml 和 prompts/。改完后，在 UI 的状态视图点 Reload，或者运行 weir-axi reload。两者调用的是同一个 HTTP 接口。

    • reload 先等正在跑的 sync 和 AI 调用结束，再重新读取并校验全部 config，包括 prompt 文件和每个 plugin 的 configSchema。
    • 校验通过，就按新 config 重建 source、AI profile、bucket 和 rule，继续 sync 和 enrich。
    • 校验失败，接口返回错误，列出出错的文件和 config 路径。daemon 不会退回上一份 config。sync 和 enrich 停下，UI 和 axi 仍然能读已有的数据，状态视图和 axi 首页都显示这个错误。改好之后再 reload 一次。
    • 启动时校验失败，daemon 打印错误后退出。
    • port 改了要重启 daemon 才生效。

    不做设置页，只做状态视图

    设置页难做好。enricher 的命令是 argv 数组，prompt 在单独的文件里，每个 plugin 又有自己的 schema。做成表单就得按 schema 自动生成，还要把改动写回 TOML 并保留注释。weir 的用户本来就带着 agent。「帮我加一个 bucket」让 agent 改 config.toml 更快。

    UI 需要的是一个只读的状态视图，回答「它现在靠不靠谱」。它的入口是灵动岛上一个小的状态按钮，展开和收成药丸时都在。一切正常时它不显眼。任何一个 source 出错，或者 config 有错，它上面出现一个琥珀色圆点，药丸形态也看得到。

    没打开 conversation 时，阅读区直接显示一份紧凑的状态摘要，列出每个 source 上次 sync 的时间、enrich 队列还剩多少，以及错误。有错误时，摘要里的 Open Status 按钮打开下面这个完整的状态视图，见第 10 节。

    点状态按钮后，状态视图在阅读岛里替换阅读内容，就像打开一个 conversation。它不加第三栏，两栏也不动。按 Esc 或关闭按钮，回到原来的内容和阅读区的滚动位置。视图分四块：

    • Sources。每个 stream 上次 sync 的相对时间，比如 Synced 3m ago，以及 item 数。出错时显示 Sync failed 和最近一次错误的原文。
    • Enrichment。还有多少 conversation 等着 enrich，上次运行的时间和耗时，用的是哪个 AI profile，最近一次失败和它的日志路径 ~/.weir/logs/enrich/<file>.txt。
    • Config。config.toml 的路径，加载时间，Reload 按钮。点 Reload 后按钮显示 Reloading…，daemon 先等正在跑的 sync 和 AI 调用结束。成功时显示 Config loaded 和新的加载时间。失败时列出每个错误的文件和 config 路径，显示 Sync and enrich stopped，灵动岛上出现琥珀色圆点。conversation 照样能读。改好后再点一次 Reload，错误就清掉。
    • Appearance。主题，三个选项 System、Light、Dark，选择存在 localStorage。

    两栏从一开始就在，打开 conversation 时都不动

    • 整体宽度上限 1360px，居中。宽屏两侧的背景始终不变。
    • 左栏是平的，直接铺在背景上，列出当前 bucket 的 conversation。右栏是一块浮起的阅读岛。
    • 打开、切换、关闭 conversation 时，两栏的位置和大小都不变，只有阅读岛里的内容在换。原型第 4 轮实测，在 2560 宽的屏幕上打开一条 conversation，阅读区以外只有 1.16% 的像素变化，就是被选中的那一行。之后灵动岛改矮了，这个数没有重测。
    • 阅读区空着时，也就是没打开 conversation 时，显示一份紧凑的状态摘要。每个 source 一行，写上次 sync 的相对时间，比如 Synced 3m ago，出错时写 Sync failed 和错误原文。Enrichment 一行写 4 conversations waiting 或者 Caught up。config 加载失败时多一句 Sync and enrich stopped. The config did not load.。有错误时下面有 Open Status 按钮，打开完整的状态视图。这份摘要取代了原来的「数据更新于」那一行。页面加载时不自动打开 conversation，因为打开就算已读。
    • 原型第 12 轮试过在空阅读区放一份 AI 写的 bucket 简报。引用只靠头像，PR 那一行下面是 12 个一样的 GitHub 图标，分不清对话。FYI 的一行还把一条不相关的防诈骗提醒混进了 PR 那一组。所以否决了，以后也不做。

    灵动岛嵌在阅读岛上沿，只负责导航

    • 没打开 conversation 时，灵动岛展开成一句话，列出每个有更新的 bucket 和它的数量。一个 bucket 时是 13 Action has updates.，两个时是 13 Action and 12 FYI have updates.。三个及以上时用逗号隔开，最后一个前面用 and，and 前面不加逗号，比如 15 Action, 12 FYI, 8 Reading and 31 Alerts have updates.。全部读完时是 All caught up.。每个 bucket 是一个小部件，带几个发件人头像、数量和名字。点它就切到那个 bucket。
    • 一次只看一个 bucket，这是原型里的导航方案 B。「未分类」排在最前面。已读完的 bucket 和「已清理」放在句子后面的尾句里，同样可以点。bucket 多时，这句话直接折行，不收成「and N more」。
    • 「已清理」的小部件一直显示，数量是 0 时也在。展开的句子和药丸里都有。空阅读区只显示状态摘要，不放「已清理」。
    • 打开 conversation 后，灵动岛收成一行药丸，只剩各 bucket 的小部件和数字。读长文时它不占地方。
    • 药丸两端固定。左端是搜索按钮，右端是「已清理」和状态按钮。中间的 bucket 区放不下时横向滚动，被藏住内容的那一侧边缘渐隐，渐隐处叠一个箭头按钮。点一次箭头，滚动距离是可见宽度减去两侧渐隐的 64px，只用鼠标也能翻到最后一个 bucket。箭头不占 Tab 顺序，键盘用户直接 Tab 到各个 bucket 小部件。当前 bucket 的小部件滚到中间。鼠标的竖向滚轮在这里也变成横向滚动，触控板的横向轻扫照常生效。

    • 灵动岛上还有搜索按钮和状态按钮，展开和药丸两种形态都有。搜索见下文，状态视图见第 09 节。

    阅读区先讲新进展，再讲原文

    打开一个 conversation，阅读区按顺序回答四个问题：这是什么事，上次之后有什么新进展，和我有什么关系，原文怎么说的。

    • 顶部是标题和 summary。下面是「自你上次查看」，左边一条直的 3px 竖线，没有底色和圆角。
    • 再下面是 points，按 ask、decision、date、info 分组。
    • 对话流里，每个气泡是一条 gist，不是原文。你自己的消息靠右。
    • 换人或者停顿超过 5 分钟就开一个新组。组头依次是名字、来源和时间，比如「Jacky Ng Gmail 14:03」，和 Slack、Teams 一样。你自己的组不显示名字。气泡里不放时间。
    • 来源标签只在变化时出现。一个全是邮件的 conversation，通常只在第一组显示一次 Gmail。中间有折叠行时，折叠行之后会再显示一次。
    • 打开时直接落在第一条未读。连续超过 3 条的已读消息折叠成一行「之前 N 条」，只留最后 1 到 2 条可见。
    • 界面上不出现任何语言名。原文对照的两栏叫「摘要」和「原文」。

    底部有一条悬浮的 dock，按钮是「完成」「标为未读」「静音」「原文」，以及「在 Gmail 中打开」。「标为未读」只在已读时出现。最后一个按钮里的来源名由 stream 的 openLabel 提供，所以 Teams 的 conversation 显示「在 Teams 中打开」。

    「原文」打开整段对照，而不是单条原文

    • 对话框和整个舞台一样宽。左栏按顺序列出 gist，右栏是原文岛，两栏一起滚动。原型实测，打开时定位的那一条在两栏的落点误差小于 0.5px。其他消息在两栏里的位置并不逐行对齐。
    • 打开时定位到阅读区当前能看到的第一个气泡，接着你正在读的位置。
    • Esc、关闭按钮、点对话框外面，三种方式都能关。关闭后阅读区停在原来的滚动位置，焦点回到「原文」按钮。

    「完成」是让 conversation 离开视线的唯一方式

    • 看过的 conversation 变灰，但还留在列表里。点「完成」它才消失，并且自动打开下一条。
    • 每个 bucket 都有「全部清掉」。alerts 这类 bucket 里常有上百条，没有它清不完。
    • 「已清理」视图能找回所有完成和静音的 conversation，每条都有「恢复」。
    • 完成的 conversation 来了新消息，会以未读状态重新出现。静音的不会。

    搜索也在灵动岛里，一条结果就是一个 conversation

    原型第 10 轮比了三种放法。搜索放在灵动岛里，放在左栏顶部，或者弹出一个带预览的面板。定稿用灵动岛这一种，再从另外两种各借了一点。匹配规则和 weir-axi search 相同，见第 05 节。

    • 进入。点灵动岛上的搜索按钮，或者按 /，灵动岛变成输入框。两栏的位置和大小都不变。
    • 结果那句话。边输入边更新。灵动岛那句话变成结果句，语法和 bucket 那句话相同，比如 “freeze” appears in 1 Action and 2 Reading.。有已完成或静音的结果时，句子里多一个「已清理」小部件。点一个小部件，结果只剩那一组。没有结果时显示 Nothing matches “q”.。
    • 结果列表。左栏变成结果列表。一条结果是一个 conversation，最多 3 行命中，命中的词都有标记。命中在原文正文里时，显示一段约 120 字符的英文原文摘录，下面是那条消息的 gist，不读英文也能知道它在说什么。命中在 gist、summary、point、标题或发件人里时，直接显示那段文字。结果按最新一条命中消息的时间排序。
    • 范围。所有 conversation 都在搜索范围内，包括已完成和静音的。它们带一个安静的状态标签，「已完成」或「已静音」。从搜索打开时照常算已读。已完成的仍然是已完成，dock 上显示「恢复」。静音的仍然静音。
    • 阅读区。搜索时没打开 conversation，阅读岛只显示一句空状态，比如 Pick a result to read it.，不再列一遍结果。第 10 轮的灵动岛方案在这里放过一份结果简报，和左栏重复，所以删掉了。
    • 打开结果。阅读区落在第一条命中的消息上。这条消息要是在折叠行里，折叠行会展开。气泡里命中的词有标记。只在原文里命中的气泡带一个小标记。灵动岛收成药丸，显示查询、计数 1/4，以及上一处、下一处、关闭三个按钮。点「原文」，对照框落在当前这一处，原文里的词也有标记。
    • 离开搜索。按 Esc、清空输入框或点关闭，都回到搜索前的 bucket、搜索前打开的 conversation，以及左栏原来的滚动位置。
    • 字段 chip。在输入框里写 from:、in:、source: 开头的词，按空格或者离开输入框后，它变成一个可以删掉的 chip。三种 chip 对应 weir-axi search 的 --from、--bucket、--source，和其他词是 AND 的关系。in: 后面写 bucket 的 id 或显示名都行，不分大小写。输入框空着时按退格，删掉最后一个 chip。
    • 只搜新写的正文。原文只搜 body_new。一条回复不会因为它引用的旧文字而命中。所以落点那条消息的原文里，一定看得到这个词。
    • 标记的颜色。深色主题的标记用琥珀色，比黄色在近黑的底色上安静。两种主题下，标记里的文字对比度都要达到 WCAG AA 的 4.5。

    主题默认跟随系统，也可以在状态视图的 Appearance 里固定为 Light 或 Dark，选择存在 localStorage。bucket 颜色在两种主题下各有一套。气泡统一用中性底色，不带 bucket 颜色。定稿原型用脚本测了文字对比度，深色最低 5.63，是搜索命中的琥珀色标记。浅色最低 5.18，是状态视图里的 Config loaded。都高于 WCAG AA 的 4.5。

    • 不要用 text-wrap: pretty。WebKit 会把整段中文的行长拉平，每行都提前换行，右边空出大片参差空白。只在短标题上用 balance。

    • 列表行在原型里能用 Tab 聚焦，但在辅助功能树里不是按钮角色。正式版要改成真正的按钮或链接。
    • 标签页标题显示未读总数，比如 (3) weir。

    11weir-axi 是 agent 唯一的入口

    weir-axi 是一个 CLI，调用本机的 HTTP API。它遵循 AXI 的原则：不带参数直接运行就显示当前状态，长正文默认截断并提示 --full，每次输出后附上 help[]，列出下一步可以运行的命令。输出格式是 TOON。

    命令作用
    weir-axi各 bucket 的未读数和待完成数，各 source 的 sync 状态，config 错误
    weir-axi search <query>和 UI 的搜索用同一套匹配。两者查同一张 search_fts，原文只搜 body_new，所有词都在同一个 conversation 里出现才算命中，见第 05 节。可以用 --bucket、--source、--from、--since 过滤
    weir-axi conv <id>一个 conversation 的 summary、points 和每条 item 的 gist
    weir-axi item <id> [--full]一条 item 的原文
    weir-axi enrich --conv <id> | --since <dur>手动重算
    weir-axi reload重新读取并校验 config，失败时输出错误位置

    12安全边界是「只读」和「不信任消息内容」

    邮件和群聊的内容是外部人写的，属于不可信输入。如果一个 agent 同时具备三样能力，就构成一条数据外泄路径：读得到你的私人数据，会读到外部内容，还能往外发消息。weir 的设计在每一层都切断其中一样。

    • MVP 不实现任何 source 写操作，所以 weir 本身发不出消息。
    • AI profile 的示例命令带 --no-tools。enricher 调用的 AI 只能输出文本，不能执行操作。
    • prompt 里用分隔符把消息内容标为数据，并告诉 AI 不执行其中的任何指令。
    • enricher 的输出必须通过 Schema 校验。字段以外的内容一律丢弃。
    • daemon 只监听 127.0.0.1。
    • 凭证不进 SQLite，用 *_cmd 从 Keychain 或环境变量取。

    以后如果加 source 写操作，第一个做「把已读同步回 source」，它风险低、价值高。即使做了，也默认只能由人在 UI 里点击触发，不通过 axi 开放给 agent。

    store/        SQLite、FTS5、migration
    sync/         scheduler、plugin 加载、upsert、按 thread 归属、rule
    enrich/       dirty 查询、防抖、攒批、合并、CLI 调用、输出校验
  plugins/
    imap/
  apps/
    daemon/       进程入口、HTTP API、config 加载和 reload
    web/          Web UI
    axi/          weir-axi

    建议按这个顺序搭，每一步都能单独验证：contract 和 store，然后 imap plugin 加 sync，然后 HTTP API 加 weir-axi search，然后 enrich，最后 Web UI。做完第三步，agent 就已经能搜你的邮件了，那时还没有任何 AI 调用。
