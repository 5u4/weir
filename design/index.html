    weir 设计稿

    2026-10-28 · 依据多轮原型的结论 · 原型代码在同目录的 prototype/，属于一次性代码 · 原型跑在仓库里的合成数据 prototype/data/scenarios.json 上，不读真实邮件

    weir 是一个跑在你本机的 daemon。它把多个 source 的消息同步进一个 SQLite 文件，按 conversation 聚合，再按你写的 rule 给 conversation 打 tag。带 AI 的 tag 下，新消息攒够一定字数，weir 就调用你自己配置的 AI 写一份 digest。你在 localhost 的 Web UI 里看，你的 agent 通过 weir-axi 查。

    weir 只读。它不会改 Gmail、Outlook 或 Teams 里的任何状态。已读、完成、静音都只记在本地。

    整个设计靠一个想法成立：sync 和 digest 分开跑。conversation 和 tag 在 sync 时就由结构和 rule 定下来，不调用 AI。所以新消息一进来就能看到、能搜到，原文就是气泡。digest 稍后异步补上。AI 慢一点、贵一点，甚至完全不配，都不影响主体验。

    01weir 负责同步、聚合和打 tag，不负责回复

    weir 要解决的是「想知道，但不用动」的那一层信息。比如别人的 PR 合了、某个群在讨论架构、build 挂了但不归你管。逐封点开太累，全部忽略又怕错过。weir 把它们收进一个地方，长对话用你读得快的语言写成 digest，读完一键让它离开视线。

    它是个人工具，也是开放的。AI 和 source 都由用户自己接入，weir 不绑定任何一家。

    本文用到的术语

    下表的术语在全文中保持英文，含义只有一个。

    术语含义
    source一个已配置的数据来源，比如「我的 Gmail」。由一个 plugin 实现。
    plugin实现 source 接口的代码，比如 gws。同一个 plugin 可以配置成多个 source。
    streamsource 里的一路数据，比如一个 Gmail 邮箱。以后 Teams 的 source 里，一个 chat 或频道是一个 stream。
    item一条消息，比如一封邮件或一条 Teams 消息。
    thread_idsource 给出的分组，比如一个 Gmail thread。可以为空。
    container_id消息在哪里说的。Gmail 是邮箱地址，Teams 是一个 chat 或频道。
    conversation同一个 source 里 thread_id ?? container_id 相同的 item。sync 时按结构定下，不调用 AI。是 UI 和 digest 处理的基本单位。
    tag用户在 config 里定义的标签，比如 work。由 rule 算出，一个 conversation 可以带多个 tag。没有内置 tag。
    ruletag 的匹配条件，对单条 item 求值。conversation 里任意一条 item 命中，conversation 就带这个 tag。
    Untagged一个 tag 都没命中的 conversation 所在的视图。它不是 tag，config 里不写。config 里一个 tag 都没有时，所有 conversation 都在这里。
    AI profileconfig 里一个有名字的 AI CLI 命令。[digest] ai 按名字引用它。
    digestAI 对一个 conversation 里一段连续 seq 写的摘要，由一句 headline 和若干 topic 组成。写好就不变，同一个 conversation 的 digest 互不重叠。
    topicdigest 里的一件事，有标题、状态（open、resolved、fyi）、正文，以及它涉及的 item seq。
    seqitem 写进数据库的顺序号，全局递增。已读、完成和 digest 的范围都用它。
    ai_since一个 ai = true 的 tag 第一次以 ai = true 加载的时间。自动 digest 只处理 occurred_at 不早于它的 item。存在 tag_state 里。

    02一封新回复从进来到被你清掉，一共经过八步

    本节跟一个具体例子走完全程，后面各节都会引用它。假设如下：你配置了 gws source personal-mail。tag work 写了 ai = true，rule 是发件人地址以 @northwind.example 结尾，或者标题含 Northwind。conversation「Northwind 迁移与验收」是一个 Gmail thread，里面早有客户的邮件，所以带着 work。它上一份 digest 的 to_seq 是 9120。seq 全局递增，所以同一个 conversation 里的 seq 不连续。之后这个 conversation 又进来两封短邮件，seq 是 9154 和 9188，一共 600 字符，还没到阈值。你昨天看完后点了「完成」。今天 14:03，客户回了一封 900 字符的邮件，seq 是 9311。

    1. sync 拉到这封邮件。scheduler 每 5 分钟调用一次 plugin 的 sync(stream, cursor)，间隔由 sync_every 决定。gws plugin 从上次的 Gmail historyId 起读 history，返回一条 item，thread_id 是 Gmail 的 thread id，body 是转成 markdown 的正文，bodyNew 是去掉引用历史和签名后的正文，raw 是去掉正文和传输、签名头之后的 API 返回。core 按 (stream_id, external_id) upsert，重复 sync 不会产生重复 item。新 item 拿到一个 seq，同时记下 synced_at。core 把 bodyNew 写进 body_new，FTS index 同时更新。从这一刻起，UI 和 weir-axi search 都能搜到它。已有的 item 再次 upsert 时，比如 Gmail 加了或去掉一个 label，保留原来的 seq，字段、raw、body_new 和 FTS 行一起替换。last_seq 不变，所以 conversation 不会重新出现，也不会变成未读。tag 怎么跟着变，见第 06 节。
    2. 按结构挂进 conversation。conversation 的 key 是 source 加上 thread_id ?? container_id。这封邮件的 thread 已经有 conversation，它直接挂进去。这一步不调用 AI。
    3. 对新 item 跑 tag rule。core 用每个 tag 的 rule 匹配这一条 item。命中的 tag 加到 conversation 上。已有的 tag 不会因为新 item 没命中而去掉，因为一条命中就够。这里 work 本来就在。
    4. conversation 立刻重新出现。conversation 的 last_seq 变成新 item 的 seq，比昨天「完成」记下的 cleared_seq 大。所以它回到 work 视图，状态是未读。灵动岛那句话里的计数加一，标签页标题变成 (1) weir。这一步没有后台任务，是查询时算出来的。此时阅读区里，上一份 digest 之后的三封邮件还是原文气泡。
    5. 算待 digest 的字数。conversation 带 ai = true 的 tag，所以走自动 digest。起点是上一份 digest 之后、occurred_at 不早于 ai_since 的第一条 item。从起点到最后一条，body_new 一共 1500 字符，过了 1000 的阈值。没有安静期，也没有定时器，条件一成立就排进 digest 队列。
    6. AI 写一份 digest。输入是这三封邮件，加上它们前面约 6000 字符的上下文。上下文里已经被 digest 覆盖的部分用 digest 代替。AI 输出一句 headline 和几个 topic，每个 topic 列出它涉及的 seq。core 校验后插入一行 digest，范围从 9154 到 9311。
    7. 你打开它。上次读过的 digest 各收成一行。这份新 digest 是一张卡片，有 headline 和 topic。topic 下的「N originals」能把原文展开在原处。阅读区只有这一种视图，原文要么在 topic 下展开，要么是还没 digest 的原文气泡。打开本身不算已读。消息滚进视口才算读过，seen_seq 前进到看过的最大 seq，读到底时等于 last_seq。
    8. 你点「完成」。cleared_seq 前进到 last_seq，conversation 离开列表，下一条自动打开。灵动岛里的计数跟着变，没有别的提示，也没有撤销。点错了就去「已清理」里点「恢复」。

    四个变体，各自在不同的步骤分叉：

    • 新开的 thread在第 2 步分叉。没有同 key 的 conversation，sync 新开一个，标题用 item 的标题。第 3 步照常跑 rule。见第 06 节。
    • 没有 AI tag 的 conversation在第 5 步分叉。比如只带 github 这种 ai = false 的 tag，或者一个 tag 都没有、落在 Untagged。它不自动 digest，阅读区全是原文气泡。你想要摘要时，点「Digest now」手动写一份。
    • 字数没到阈值在第 5 步停下。新邮件只是原文气泡，等下一封邮件把字数推过阈值。不想等就点「Digest now」。
    • agent 查询不经过第 7、8 步。agent 运行 weir-axi，首页显示 work 有 1 个未读。weir-axi conv <id> 读到同样的 digest 和原文。axi 读取不改变已读状态。

    04Source plugin 只交出数据，不做判断

    一个 plugin 对外暴露三样东西，由不同的人负责：

    部分谁提供例子
    config schemaplugin 定义，用户填写command、backfill
    stream descriptorplugin 声明，用户不用管id、kind、名字、代表「我」的地址
    syncplugin 实现按 cursor 增量拉取

    接口是普通的 async 函数加纯数据。plugin 作者不需要会 Effect。core 在内部把它包成 Effect，并用 Schema 校验 plugin 的返回值。

    几条约定：

    • configSchema 用 Standard Schema。plugin 作者可以用 zod、valibot 或 Effect Schema 写。Effect Schema 用 Schema.toStandardSchemaV1 导出 Standard Schema（effect 4.0.6）。
    • daemon 启动和 reload 时，用 configSchema 校验 [source.config]。校验失败的报错里带上出错的 config 路径。
    • cursor 的内容由 plugin 决定，比如 Gmail 的 historyId，或者 Graph 的 delta token。core 只负责保存，不解析。
    • more = true 表示还有下一页，core 立刻用新 cursor 再调一次。这样冷启动拉一万封邮件时，每一页都单独落盘，中途崩溃也能从上一页接着来。
    • body 和 bodyNew 都是 markdown。把 source 的原始格式转成 markdown 是 plugin 的事，core 和 UI 只认 markdown。bodyNew 是去掉引用历史和签名后的正文。plugin 可以自己算，返回 null 时 core 用通用实现。
    • openLabel 是 dock 上「在 Gmail 中打开」按钮里的来源名。
    • me 列出这个 stream 里代表你的地址或 handle。core 用它算 fromMe。你发的消息靠右显示，digest 里用「你」称呼你。
    • RawItem 不带收件人、抄送和 @ 提及，也不带 attrs 或 labels 这类整理过的字段。需要这些信息的 rule 直接读 raw。
    • plugin 用名字加载。内置的写名字，比如 gws。第三方的放在 ~/.weir/plugins/<name>/。公司内部的 source 可以放在单独的私有仓库，不碰主仓库。

    gws plugin 通过 gws CLI 读 Gmail

    MVP 唯一的 source plugin 是 gws。它像 AI profile 一样，把 gws（Google Workspace CLI）当成 argv 命令调用。OAuth 由 gws 负责，token 存在 gws 自己的 keyring 里。weir 碰不到任何凭证。

    • [source.config] 有两个字段。command 是 argv，默认 ["gws"]。backfill 是一条 Gmail 搜索语句，比如 newer_than:30d，用于冷启动，以及 history 过期后的重新列表。
    • 一个 source 只有一个 stream，就是整个邮箱。Gmail 没有文件夹，收件和发件只是 label 的区别（INBOX、SENT），每封邮件只有一个 message id。所以你发的邮件不用另外同步文件夹就能拉到。openLabel 是 Gmail。
    • me 是 users.getProfile 的 emailAddress，加上 users.settings.sendAs.list 里的别名。
    • thread_id 是 Gmail 的 threadId。container_id 是邮箱地址，container_name 是 Gmail。每封 Gmail 都有 threadId，所以对 gws 来说，container 不会决定 conversation 的 key。
    • link 是 https://mail.google.com/mail/?authuser=<邮箱地址>#all/<message id>。occurred_at 取 internalDate，写成 UTC 的 ISO 时间。
    • cursor 是一段 JSON，记录当前阶段。冷启动时是 {"phase":"backfill","startHistoryId":…,"pageToken":…}，之后是 {"phase":"incremental","historyId":…,"pageToken":…}。解析不了的 cursor 直接报错。
    • 冷启动时，先用 users.getProfile 的 historyId 作为起点，再用 backfill 调 users.messages.list，对每个 id 调 users.messages.get format=full。分页靠 more = true。列表拉完后 cursor 进入 incremental，从这个起点读 history，所以冷启动期间到达的邮件不会漏掉。
    • 正文取 text/html 部分，用 turndown 转成 markdown。文字原样保留，不转义 markdown 符号。链接文字和地址相同时只写地址。邮件没有 HTML 部分时，取 text/plain，按原型 originalMd 的规则整理成 markdown。每行保留换行，只有真正的列表、表格、引用和 diff 才按 markdown 结构处理。有文件名或带 Content-Disposition: attachment 的 part 是附件，它和它下面的所有 part 都不算正文。每个 part 按自己 Content-Type 里的 charset 解码，没写或者认不出时按 UTF-8。
    • bodyNew 由 plugin 自己算，不返回 null。HTML 邮件先删掉 gmail_signature、gmail_quote 和 gmail_attr 这几个 class 的元素再转换。纯文本邮件在第一处 -- 签名分隔行截断；一行 On … wrote: 后面紧跟 > 开头的行时，也在这一行截断。
    • 之后增量同步，调 users.history.list startHistoryId=<cursor>，读 messageAdded、messageDeleted、labelAdded、labelRemoved 四种记录。新的和 label 变了的 message 都用 messages.get format=full 重新拉一遍，这样 raw.labelIds 总是最新的。一页里同一个 id 只拉一次，同一页里既新增又删除的 id 只算删除。
    • 冷启动列表默认不含带 SPAM 或 TRASH label 的邮件。重新拉到的邮件带 SPAM 或 TRASH，或者 messages.get 返回 404，或者 history 里记着它被删掉，都成为一条 deletions。
    • gws schema gmail.users.history.list 写明，historyId 一般至少一周有效，少数情况下只有几个小时，收到 HTTP 404 时应用应当做一次完整同步。所以收到 404 时，plugin 以这次 users.getProfile 的 historyId 为新起点，重新从 backfill 列表的第一页开始。upsert 按 (stream_id, external_id) 幂等，重拉不会产生重复 item。history 过期期间被删除或移进 SPAM、TRASH 的邮件不会出现在重拉的列表里，plugin 也就发不出它们的 deletions，这些 item 会留在 weir 里。要清掉它们，core 得拿已存的 id 和 backfill 范围对账。等 contract 有了对账信号再做，比如一个「完整重列」标记，core 据此删掉范围内这次没列出来的 id。
    • gws 退出码不为 0 时，plugin 抛出 GwsError，带上退出码，以及 stdout 里 {"error":{code,message,reason}} 的内容。stdout 不是这个格式时，message 取 stderr；stderr 也为空时，message 是 exited with code N。

    raw 存什么由 plugin 决定

    tag rule 可以用 JSON Pointer 指向 raw 里的任何字段，比如 Gmail 的 labelIds 或某个邮件头。raw 里留哪些字段由 plugin 决定。正文已经转成 body 和 bodyNew，不必在 raw 里再存一份。rule 要匹配正文时读输入里的 body。

    gws 存的是 messages.get format=full 的返回，去掉两样东西。一是每个 MIME part 的 body.data，也就是 base64url 编码的正文。二是 Received、ARC-*、DKIM-Signature、Authentication-Results、X-Google-* 这类传输和签名头，以及 Feedback-ID 这类发信服务商加的头。labelIds、其余邮件头和 MIME 结构都保留。下面的数字在作者邮箱上测得，仓库内不可复现。作者的 240 封 Gmail 原样存平均每封 47.3 KB，其中 body.data 占 85.5%。两样都去掉后平均每封 2.5 KB，一万封约 25 MB。完整的头部列表在 design/prototype/data/raw-size.ts 里。它的参数是一个目录，里面放 messages.get format=full 的 JSON 文件，用法是 bun data/raw-size.ts <dir>。

    plugin 和 rule 都归用户自己。plugin 改了 raw 的形状，比如多删一个字段或换了拉取格式，依赖它的 rule 会静默失效。weir 不检测，也不报警。plugin 的文档写明它存了什么。MVP 不压缩 raw，也不按时间清理旧数据。

    容易误解的地方 你可能以为 conversation 要由 AI 判断哪些消息在说同一件事。它不是。conversation 只看结构，key 是 source 加上 thread_id ?? container_id。一封邮件的 thread 就是一个 conversation。Teams 的一个 chat 或一个频道整体是一个 conversation，不按频道里的回复串拆开。频道帖子的 thread_id 照样存下来，只用来显示「回复了哪条」。一个群里同时聊五件事，由 digest 的 topic 分开，不由 conversation 分开。

    每条 item 都带 thread_id 和 container_id 两个字段，两者含义固定。thread_id 可以为空，Teams 群聊里的大部分消息就没有。

    kind 在 MVP 里只有 message。日历以后作为 event kind 加入，那时加一张 event_detail 表。

    05存储按生命周期分层，只有用户层不能丢

    所有数据都在 ~/.weir/weir.db 一个文件里。表按生命周期分成五层。判断某张表能不能删，只要看它属于哪一层。

    层内容丢了怎么办
    原始层stream、item从 source 重新 sync
    派生层conversation、conversation_tag从 item 和 config 重算，不调用 AI
    AI 层digest能重新生成，但要花 AI 费用，写出来的内容也会不同
    用户层conversation_state、tag_state找不回来，需要备份
    运维层sync_run、digest_run直接丢

    搜索索引 search_fts 不属于这五层。它只是索引，丢了就从 item 和 digest 重建，不用 sync，也不用调用 AI。

    tag_state 放在用户层，是因为丢了它，每个 AI tag 的 ai_since 会被重置成丢失之后的那一刻。中间这段时间的消息就不再自动 digest。

    daemon 或 agent 需要知道的放 SQLite，导航放 URL，其他放 localStorage

    搜索用 trigram 索引，不到 3 个字的词改用 LIKE

    搜索要同时对中文和英文有效。FTS5 默认的 unicode61 分词器两样都做不到。它把一串连续的汉字当成一个词，「报价」只在单独出现时才搜得到。英文它只按整词匹配，migrat 搜不到 migration。trigram 分词器按 3 个字一组建索引，3 个字及以上的词都能按子串搜对。不到 3 个字的词它一条也搜不到，而两个字的中文词恰恰是最常见的查询。

    所以每个词按长度分开处理。下面的数字在作者邮箱上测得，仓库内不可复现。范围是 301 条 item 的 body_new 和当时每条 item 的一句话 AI 摘要，SQLite 3.54.0，通过 bun:sqlite：

    查询实际条数unicode61trigramLIKE
    报价124012
    保险报价3033
    migrat1101111
    PR245880245

    「实际条数」是对同样两个字段做不分大小写的子串匹配得到的。LIKE 在每个查询上都和它一致。LIKE 要扫全表，每次查询 0.80 ms，trigram 的 MATCH 是 0.022 ms。两个数都是 200 次查询的平均，只跑了一轮。301 条上 LIKE 不慢，但它的耗时随条数增长，所以只给短词用。现在索引的是原文和 digest，文字构成变了，但分词器的结论不受影响。

    • 索引用 tokenize = 'trigram case_sensitive 0'，不分大小写。
    • 查询按空白切成词。3 个字及以上的词用 MATCH，词放进双引号，不当成 FTS 语法解析。不到 3 个字的词用 text LIKE '%词%'，先转义 % 和 _。字数按字符算，不按字节算。
    • 每个词各查出一组 conversation id，再取交集。也就是所有词都要在同一个 conversation 里出现，但可以出现在不同的消息、不同的 digest 和不同的字段里。
    • 原文只索引 body_new，不索引引用历史。一条回复不会因为它引用的旧文字而命中。
    • --from、--tag、--source、--since 和 UI 里的 chip 是普通的 SQL 条件，作用在交集上。
    • 命中的是哪条消息、哪份 digest、哪个字段，索引不记。API 只对要显示的结果逐个字段再比一次，用来生成命中行和标记。
    search_fts 的结构，以及为什么只用一张表 
    CREATE VIRTUAL TABLE search_fts USING fts5(
  text,
  conversation_id UNINDEXED,
  item_seq UNINDEXED,
  digest_id UNINDEXED,
  tokenize = 'trigram case_sensitive 0'
);

    表里有两种行。

    行指向text 的内容谁来写
    每条 item 一行item_seq标题、发件人名字和地址、来源名、body_newsync 写入。再次 upsert 时替换。软删除时删掉
    每份 digest 一行digest_idheadline，每个 topic 的标题和正文写 digest 时写入。Redo 替换 digest 时重写
    • 一张表就够。查询的单位是 conversation，每个词只要一次查询就拿到 conversation id。拆成 item 和 digest 两张表，每个词就要查两次再合并。
    • text 只有一列。哪个字段命中只在显示结果时才需要，那时 API 会逐个字段重新比较，所以不用每个字段一列。
    • item 单独成行，不把整个 conversation 拼成一行。长群聊来一条新消息，sync 只写这一条的行，不用重写整个 conversation。
    • 不用 external content 表。文字来自 item 和 digest 两张表，external content 只能对着一张表或视图。所以 core 在写这两张表的同一个事务里写 search_fts，不用 trigger。代价是文字存了两份。

    水位线用 seq，不用时间

    「完成」如果只记一个时间，之后只有比它新的消息才会让 conversation 重新出现。问题出在晚到的消息。Mac 睡眠或者 daemon 停了几个小时，之后的 sync 才拉到一封早上发出的邮件。它的 occurred_at 早于你点「完成」的时间，按时间比较就不会重新出现。

    所以水位线比较的是 seq，也就是写进数据库的顺序。只要是 weir 之后才知道的消息，seq 一定更大。显示时间仍然用 occurred_at。digest 的范围也用 seq 表示，所以晚到的消息排在已有 digest 之后，不会插进它们中间。

    conversation 的 key 只看结构

    • key 是 source 加上 thread_id ?? container_id。有 thread_id 就按 thread 分，没有就按 container 分。
    • 邮件的一个 Gmail thread 是一个 conversation。Teams 的一个 chat 或一个频道是一个 conversation。
    • key 里带 source，所以一个 conversation 只来自一个 source。MVP 没有跨 source 的 conversation。
    • AI 不参与。没有「先开一个临时 conversation，等 AI 决定要不要合并」这一步，也就没有「正在分拣」的中间状态。
    • MVP 不能手动移动 item。digest 记的是一段连续的 seq，把 item 移走会让已写好的 digest 失真。移动和合并留到以后，见第 14 节。

    tag 是派生数据，任意一条 item 命中就算

    • rule 对单条 item 求值。conversation 里只要有一条 item 命中，conversation 就带这个 tag。
    • 一个 conversation 可以同时带几个 tag，在每个 tag 的视图里都出现，各个 tag 的计数会重叠。
    • 一个 tag 都没命中的 conversation 出现在 Untagged 视图。这样 config 里一个 tag 都没写时，所有消息也都看得到。
    • source 没有内置视图。想按 source 看，就写一个 tag，rule 是 /source 等于那个 source 的 id。
    • tag 只由 item 和 config 算出。启动和 reload 时整体重算，存在 conversation_tag 里只是为了列表查询快。改 rule 不需要 migration。
    • 新 item 只会给 conversation 加 tag。已有 item 再次 upsert 时，比如 Gmail 上去掉了一个 label，core 按这个 conversation 的全部 item 重算 tag。conversation 可能因此失去一个 tag，离开那个视图。
    • 没有内置 tag，也没有内置的「Me」。默认 config 里只有 source，一个 tag 都没有，所以开箱不调用 AI，所有 conversation 都在 Untagged。

    07digest 按字数自动生成，从不自动重算

    digest 是 weir 唯一的 AI 输出。它把一段连续的消息写成一句 headline 和几个 topic，替你读完原文。下面的形状写好就不变：

    type Digest = {
  conversationId: string
  fromSeq: number                 // covers every item with fromSeq <= seq <= toSeq
  toSeq: number
  headline: string                // one sentence, in [digest] language
  topics: {
    title: string
    state: "open" | "resolved" | "fyi"
    body: string
    seqs: number[]
  }[]
  trigger: "auto" | "manual"
  aiProfile: string
  createdAt: string
}
    • 同一个 conversation 的 digest 互不重叠，中间允许有空隙。空隙里的 item 显示为原文。
    • 字数一律按 body_new 的字符数算，也就是去掉引用历史后的正文。
    • 本节的阈值和字数都是起始值，没在真实数据上调过。三个值都在 [digest] 里配置，见第 09 节。

    自动 digest 只看数据库里已有的行

    只有带 ai = true tag 的 conversation 自动 digest。每次 sync 写完，core 对受影响的 conversation 算下面几个值：

    1. since 是这个 conversation 上所有 AI tag 的 ai_since 里最早的一个。
    2. floor 是这个 conversation 所有 digest 的 to_seq 最大值，自动和手动的都算。没有 digest 时是 0。
    3. start 是大于 floor、而且 occurred_at 不早于 since 的最小 seq。
    4. 待 digest 字数是 seq 从 start 起所有 item 的 body_new 字符数之和。
    5. 字数达到 threshold，默认 1000，就立刻为 [start, last_seq] 写一份 digest。

    没有安静期，没有最长等待，也没有两次之间的最小间隔。所有值都由数据库里已有的行算出，不存进度字段。daemon 崩溃或重启后再算一遍，得到的是同一个范围。

    比较 ai_since 用的是 occurred_at，不是 synced_at。冷启动时历史邮件是启动之后才 sync 进来的，按 synced_at 比较会把整个历史都送去 digest。按 occurred_at 比较，有一种边界情况：一条消息在 ai_since 之前发出、之后才收到，它不会自动 digest。这是接受的代价。

    • 冷启动不 digest 旧内容。tag 第一次以 ai = true 加载时，ai_since 记成那一刻。回填的历史都比它早。
    • 新加的 AI tag 也不 digest 旧内容。道理相同，旧消息只能看原文，或者手动 digest。
    • 冷启动回填的历史算已读，不算完成。它们不计入灵动岛的数字，但留在各自的视图里。想一次清掉一批，就写一个 tag 圈出它们，再点那个 tag 的 Clear all。规则见第 08 节。
    • 旧 thread 因为一条新 item 命中了 AI tag。只有 occurred_at 不早于 since 的 item 计入字数，也就是从这条起。

    每次调用带上前文，长范围切块

    • 上下文。每次调用都带上 from_seq 之前约 6000 字符的对话。前文里已经被 digest 覆盖的 item，用那份 digest 的 headline 和 topic 代替。没有被覆盖的 item 用原文。
    • 切块。一次调用最多送 24000 字符的 item 正文。更长的范围切成连续的几块，按顺序生成，每块各写一份 digest。后一块的上下文里带着前一块刚写好的 digest。
    • 编号。数据里每条 item 带着它的 #seq，topic 直接引用 seq。原型 digest-v3 用这种写法，549 / 553 条 item 被某个 topic 引用。这个数字在作者邮箱上测得，仓库内不可复现。

    改动只影响之后写的 digest，不自动重算。想让旧内容用上新的 prompt，就对那份 digest 点 Redo，一次一份。

    digest 的 topic 没有跨 digest 的稳定 id。旧卡片上 topic 的状态停在它写成的那一刻。一件事在后一份 digest 里变成 resolved，前一份里仍然显示 open。

    • command 是 argv 数组，不经过 shell 拼接。
    • core 拼好完整的 prompt，从 stdin 传入。prompt 包括系统指令、输出语言、guide 文件、上下文、数据，以及输出 schema。

    tag 的变更都在 reload 时生效

    操作结果
    新增 tag立刻按 rule 匹配全部 item，旧 conversation 也会带上它。
    改 rule重算，conversation 可能多出或失去这个 tag。
    调整顺序只影响显示。显示顺序就是 config 里的书写顺序，Untagged 排在最后。没有 priority 字段。

    • conversation 的 key 由结构决定，不拆分，不合并，也不能手动移动 item。
    • 不提供删除 conversation，用「完成」或「静音」代替。
    • source 那边删了邮件，item 做软删除。覆盖它的 digest 不改，要更新就点 Redo。

    已读、完成、静音由三个字段推算

    已读记在 conversation 上，seen_seq 表示读到哪一条。已读跟着视口走：一条消息滚进视口才算读过，seen_seq 前进到看过的最大 seq。打开 conversation 本身不标记任何消息。「离开视线」用的是原型里的 D1 方案，也就是手动完成。

    stateDiagram-v2
  [*] --> Unread
  Unread --> Read: scrolled to last item
  Read --> Unread: mark unread or new item
  Read --> Done: 完成
  Unread --> Done: 全部清掉
  Done --> Unread: new item
  Done --> Read: 恢复
    状态条件显示在哪里
    静音muted = 1只在「已清理」里。来新消息也不出现。
    已完成last_seq <= cleared_seq只在「已清理」里，可以「恢复」。
    未读last_seq > seen_seq它的每个 tag 视图，没有 tag 时在 Untagged。计入灵动岛那句话的数字。
    已读未完成其余情况同上，变灰，留到你点「完成」。

    表格从上到下判断，第一条命中的就是当前状态。「重新出现」不需要后台任务。新 item 让 last_seq 变大，查询结果自然就变了。「标为未读」把 seen_seq 设成 last_seq - 1。

    冷启动回填的 item 算已读。stream 的 backfilled_at 还是空的时候，也就是冷启动的每一页里，upsert 一条 item 时同一个事务把它所在 conversation 的 seen_seq 推到这条的 seq。cursor 每页都落盘，所以不能拿 cursor 是否为空来判断。最后一页提交、backfilled_at 写入之后，新 item 照常是未读。cleared_seq 不动，所以这些 conversation 留在视图里，是「已读未完成」。historyId 过期后的完整重拉不算冷启动，那时 backfilled_at 已经有值，补回来的 item 是未读。

    Rule 是一个递归的判别联合

    每个 tag 的 match 是一个 Rule。Rule 用 Effect Schema 定义，按 type 区分：

    type Rule =
  | { type: "and"; rules: Rule[] }
  | { type: "or"; rules: Rule[] }
  | { type: "not"; rule: Rule }
  | { type: "eq"; target: Pointer; is: string | number | boolean | null }
  | { type: "regex"; target: Pointer; regex: string; flags?: string }
  | { type: "exists"; target: Pointer }
  | { type: "some"; target: Pointer; rule: Rule }   // rule runs with each array element as root
  | { type: "every"; target: Pointer; rule: Rule }
    • Schema 是 Schema.Struct 组成的 Schema.Union，递归用 Schema.suspend，再用 Schema.toTaggedUnion("type") 得到穷尽的 Rule.match。解码时开 onExcessProperty: "error"，拼错的字段直接报错，不静默忽略。
    • 匹配是一个纯函数 match(rule, input) => boolean，输入是一条 item 的 { source, threadId, containerId, containerName, title, from: { name, address }, fromMe, body, raw }。source 是 config 里 [[source]] 的 id，比如 personal-mail。
    • target 是 RFC 6901 的 JSON Pointer。"" 指整个输入，/a/b 逐层取值。键里的 / 写成 ~1，~ 写成 ~0。@odata.type 这种键可以直接写。
    • 路径不存在就不匹配。eq、regex、exists、some 都是 false。every 的目标不存在或者不是数组时也是 false。
    • some 和 every 把数组的每个元素当成新的根，里面的 target 从元素算起。上面 lists 的例子就是这样找邮件头。
    • 以后再加的操作见第 14 节，包括数值比较、glob、对整个 conversation 的量词，以及「我以前给这个人写过信」这类跨 item 的历史条件。
    TOML 的一个坑 上面的 match 把嵌套的 inline table 写成了多行。TOML 1.0 要求 inline table 写在一行里，这种写法靠的是 Bun.TOML.parse 能接受它。原型实测可以解析。换 TOML 解析器之前要先确认这一点，否则长 rule 只能写成一行，或者改用 [tag.match] 子表。

    tag_state 记下每个 AI tag 从哪一刻开始

    每次加载 config，core 对照 tag_state 做两件事：

    • ai = true 的 tag 还没有行，就插入一行，ai_since 是这一刻。已有行的不动。
    • ai = false 的 tag 有行，就删掉。

    所以把 ai 关掉再打开，从打开那一刻重新算。改名的 tag 是一个新 tag，也从这一刻算。这样不管什么时候加 AI tag，都不会把历史一次性送给 AI。

    改了 config 要手动 reload

    daemon 只在启动和 reload 时读取 config.toml 和 prompts/。改完后，在 UI 的状态视图点 Reload，或者运行 weir-axi reload。两者调用的是同一个 HTTP 接口。

    • reload 先等正在跑的 sync 和 AI 调用结束，再重新读取并校验全部 config，包括 guide 文件、每个 tag 的 Rule 和每个 plugin 的 configSchema。
    • 校验通过，就按新 config 重建 source、AI profile 和 tag，重算 conversation_tag，更新 tag_state，继续 sync 和 digest。
    • 校验失败，接口返回错误，列出出错的文件和 config 路径。daemon 不会退回上一份 config。sync 和 digest 停下，UI 和 axi 仍然能读已有的数据，状态视图和 axi 首页都显示这个错误。改好之后再 reload 一次。
    • 启动时校验失败，daemon 打印错误后退出。
    • port 改了要重启 daemon 才生效。daemon 绑定端口后，把 {port, pid} 写进 $WEIR_HOME/daemon.json，先写临时文件再 rename。daemon 退出时，只有文件里的 pid 是自己的，才删掉这个文件。

    不做设置页，只做只读的 Status 视图

    设置页难做好。AI 的命令是 argv 数组，Rule 是嵌套结构，每个 plugin 又有自己的 schema。做成表单就得按 schema 自动生成，还要把改动写回 TOML 并保留注释。weir 的用户本来就带着 agent。「帮我加一个 tag」让 agent 改 config.toml，再用 weir-axi tag test 看命中了什么，更快。

    UI 用一个只读的 Status 视图代替设置页，回答「它现在靠不靠谱」。它只有两处会写东西。一是 Reload 按钮。二是 Appearance 里的主题，存在 localStorage。它的入口是灵动岛上一个小的状态按钮，展开和收成药丸时都在。一切正常时它不显眼。任何一个 source 出错，或者 config 有错，它上面出现一个琥珀色圆点，药丸形态也看得到。

    没打开 conversation 时，阅读区直接显示一份紧凑的状态摘要，列出每个 source 上次 sync 的时间、还有多少 conversation 等着 digest，以及错误。有错误时，摘要里的 Open Status 按钮打开下面这个完整的状态视图，见第 10 节。

    点状态按钮后，状态视图在阅读岛里替换阅读内容，就像打开一个 conversation。它不加第三栏，两栏也不动。按 Esc 或关闭按钮，回到原来的内容和阅读区的滚动位置。视图分四块：

    • Sources。每个 stream 上次 sync 的相对时间，比如 Synced 3m ago，以及 item 数。出错时显示 Sync failed 和最近一次错误的原文。
    • Digests。AI on 列出每个 ai = true 的 tag、它的 ai_since 和 conversation 数。Queue 列出正在跑的 digest 和等待的 conversation 数。Last run 是上次运行的时间、写了几份和平均耗时。还有 Threshold 阈值和 AI profile。
    • Config。config.toml 的路径，加载时间，Reload 按钮。点 Reload 后按钮显示 Reloading…，daemon 先等正在跑的 sync 和 AI 调用结束。成功时显示 Config loaded 和新的加载时间。失败时列出每个错误的文件和 config 路径，显示 Sync and digests stopped，灵动岛上出现琥珀色圆点。conversation 照样能读。改好后再点一次 Reload，错误就清掉。
    • Appearance。主题，三个选项 System、Light、Dark，选择存在 localStorage。

    Sources 和 Digests 读 stream、sync_run 和 digest_run。weir-axi 首页读同一份数据。

    阅读区先给新的 digest，再给原文

    打开一个 conversation，阅读区按顺序回答三个问题：这是什么事，上次之后有什么新进展，原文怎么说的。

    • 顶部是标题和 meta：带的 tag、所属的 source、这次的新消息数、消息条数、参与人数和日期跨度。一个 conversation 只属于一个 source，所以 source 只在这里写一次，不放在气泡上。参与人数是不同发件人的个数。没有「发给你」「抄送你」这类标记，因为 RawItem 不带收件人。
    • 已经读过的 digest 每份收成一行，写 headline、时间跨度和消息条数。点这一行在原处展开成卡片，卡片上有 Collapse。旧的太多时，前面的再折成一行 N earlier digests。
    • 没读过的 digest，也就是打开时 to_seq 大于 seen_seq 的，显示成卡片。卡片上是 headline、每个 topic 和 Collapse。topic 有标题、状态 chip、正文和 N originals。Collapse 把卡片收成和已读 digest 一样的一行，Last read 标记留在它上面。收起只在这次打开里有效，不存储。
    • 点 N originals，这个 topic 涉及的原文在它下面展开。展开时 topic 头吸顶，显示你读到第几条 n of N 和 Fold 按钮。
    • 只有一个 topic 的 digest，卡片上不显示 topic 标题和状态 chip，headline、正文和 1 original 照常显示。
    • 最后一份 digest 之后还没 digest 的尾巴，是原文气泡。尾巴存在时显示 Digest now。conversation 开着 AI 时，旁边还显示离阈值还差多少。
    • 原文气泡里，你自己的消息靠右。换人或者停顿 5 分钟及以上就开一个新组。每组都有头像和组头，组头是名字和时间，比如「Jacky Ng 14:03」，和 Slack、Teams 一样。你自己的组和别人的组用同一套头像和名字，只是左右镜像，头像在右边。气泡里不放时间。
    • 某份 digest 前面还没 digest 的一段原文，底部紧挨着那份 digest 有一条 Not digested、N messages above 和 Digest earlier。从新往旧翻的时候先碰到它，往前补 digest 就靠它，一次补一次调用的量。
    • 还没 digest 的每条原文气泡，悬停或聚焦时显示 Digest from here，从这条往后补到下一份 digest 之前。窄屏上点一下气泡显示。

    「完成」是让 conversation 离开视线的唯一方式

    • 看过的 conversation 变灰，但还留在列表里。点「完成」它才消失，并且自动打开下一条。
    • 每个视图都有「全部清掉」。github 这类 tag 里常有上百条，没有它清不完。
    • 「已清理」视图能找回所有完成和静音的 conversation，每条都有「恢复」。
    • 完成的 conversation 来了新消息，会以未读状态重新出现。静音的不会。

    • 进入。点灵动岛上的搜索按钮，或者按 /，灵动岛变成输入框。两栏的位置和大小都不变。

    11weir-axi 是 agent 唯一的入口

    weir-axi 是一个 CLI，调用本机的 HTTP API。它遵循 AXI 的原则：不带参数直接运行就显示当前状态，长正文默认截断并提示 --full，每次输出后附上 help[]，列出下一步可以运行的命令。输出格式是 TOON。

    weir-axi 只通过 $WEIR_HOME/daemon.json 找到 daemon 的端口，不读 config.toml。没设 WEIR_HOME 时用 ~/.weir。所以 config.toml 写坏了，weir-axi、search 这些读命令和 reload 照样连得上 daemon，reload 返回 config 错误。连不上 daemon 时，axi 输出一个 error 字段，退出码 1，错误里写出 daemon.json 的路径：

    • 文件读不到，报 daemon 没在运行，提示启动 weir-daemon。
    • 文件不是带整数 port 和 pid 的 JSON，报文件无效，提示重启 weir-daemon。
    • 文件里的端口连不上，报连不上的地址和原因，help[] 给出 weir-daemon。
    命令作用
    weir-axi各 tag 和 Untagged 的未读数和待完成数，各 source 的 sync 状态，config 错误
    weir-axi search <query>和 UI 的搜索用同一套匹配。两者查同一张 search_fts，原文只搜 body_new，所有词都在同一个 conversation 里出现才算命中，见第 05 节。可以用 --tag、--source、--from、--since 过滤

    weir-axi item <seq> [--full] [--raw]一条 item 的原文。--raw 打印存下来的 raw 对象，写 rule 时用它找 JSON Pointer
    weir-axi tag test <name>按当前 config 跑一个 tag 的 rule，输出命中的 conversation 数和几个样例。AI 帮你写 tag 时靠它验证

    12安全边界是「只读」和「不信任消息内容」

    邮件和群聊的内容是外部人写的，属于不可信输入。如果一个 agent 同时具备三样能力，就构成一条数据外泄路径：读得到你的私人数据，会读到外部内容，还能往外发消息。weir 的设计在每一层都切断其中一样。

    • MVP 不实现任何 source 写操作，所以 weir 本身发不出消息。
    • AI profile 的示例命令带 --no-tools。写 digest 的 AI 只能输出文本，不能执行操作。
    • prompt 里用分隔符把消息内容标为数据，并告诉 AI 不执行其中的任何指令。
    • digest 的输出必须通过 Schema 校验。字段以外的内容一律丢弃。
    • daemon 只监听 127.0.0.1。
    • daemon 把 Host 拆成主机名和端口再比较。主机名必须是 127.0.0.1 或 localhost，不分大小写。端口必须等于 daemon 监听的端口，省略时按 80 算，所以监听 80 时 127.0.0.1 和 127.0.0.1:80 都合格。请求带 Origin 时，它必须是 http:// 加上一个按同样规则合格的主机部分。带用户名、路径或前导零端口的值不合格，Origin: null 也不合格。不符合的请求一律回 403，正文为空。这挡住 DNS rebinding 和其他网页的跨站请求。weir-axi 不带 Origin。
    • weir 假定运行在单用户机器上，所以 HTTP API 不做身份验证，同一台机器上的其他系统账号能通过 loopback 读到邮件。要支持多用户机器，得先给 API 加按调用方区分的凭证，比如每个 daemon 一个只有本人能读的凭证，或者改用只有本人能访问的 Unix socket。
    • 凭证不进 weir。gws 把 OAuth token 存在它自己的 keyring 里。
    • 正文按 markdown 渲染时，夹带的 HTML 按文字显示，不执行，也不加载外部图片。

    以后如果加 source 写操作，第一个做「把已读同步回 source」，它风险低、价值高。即使做了，也默认只能由人在 UI 里点击触发，不通过 axi 开放给 agent。

    fake-gws 按 gws 0.22.5 的样子回答 Gmail 请求

    fake-gws 是 @weir/fixtures 的 bin，bun install 之后在 node_modules/.bin/fake-gws。它不叫 gws，不会挡住真的 gws。调用方式和 gws 相同：fake-gws [--mailbox <dir>] gmail users <resource...> <method> --params '<json>'。gws plugin 的 command 指向它，plugin、sync、store、daemon 和 axi 就都跑真代码。它只暴露 14 个 Gmail thread 里的 31 封邮件，Teams 不暴露。

    命令params返回

    messages getuserId、id、format（只支持 full）完整的 Gmail Message。正文是 multipart/alternative，含 text/plain 和 text/html 两个 part；note-to-self 那封只有 text/plain。正文开头是 scenario 的 text。发件人有签名时后面跟签名，回复后面再跟上一封的引用，GitHub 通知不带引用。邮件头带上 Received、ARC-*、DKIM-Signature 这类传输头，供 plugin 裁剪。

    getProfileuserIdemailAddress、messagesTotal、threadsTotal、historyId
    settings sendAs listuserId只有一个 robin.ellis@example.com，主地址兼默认地址
    • 成功时 stdout 输出 JSON，退出码 0。API 错误和 gws 一样：stdout 是 {"error":{"code","message","reason"}}，stderr 是 error[api]: <message>，退出码 1。不存在的 message id 和过期的 startHistoryId 都返回 404，reason 是 notFound。
    • 不支持的输入一律报错，不静默忽略：--page-all、--dry-run 这类 flag，labelIds 这类 param，full 以外的 format，q 里别的搜索词，以及没实现的命令。这些都按 gws 的校验错误处理，stderr 是 error[validation]: ...，退出码 3。
    • 不带 --mailbox 时，fake-gws 在内存里生成一个只读邮箱：31 封全部送达，now 是 FIXTURE_NOW。每页最多 10 条，比 maxResults 小时以它为准，所以默认参数下也会分页。
    • 带 --mailbox <dir> 时，状态存在 <dir>/mailbox.json，fake-gws 只读不写。改状态用 @weir/fixtures 导出的函数：seedMailbox(dir, { until? }) 送达时间不晚于 until 的邮件，其余排队，now 取 until，没给时取 FIXTURE_NOW；deliver(dir, n?) 按时间送达下一封或下 n 封；remove(dir, id) 删除；relabel(dir, id, { add, remove }) 改 label；expireHistory(dir) 让之前的 historyId 全部过期；setNow(dir, iso) 改 now。命令行的 fake-gws-seed <dir> [--until <iso>] 等于 seedMailbox。
    • until 和 setNow 的 iso 必须是真实存在的日期和时间，带时区偏移，比如 2026-02-29 或 25:00 都不行。不合法时在写 mailbox.json 之前抛错。
    • deliver、remove、relabel 每次让 historyId 加 1，追加一条 history 记录。deliver 和 relabel 还把那封邮件的 historyId 设成新值，remove 直接删掉那封邮件。relabel 没有改变任何 label 时什么都不记。expireHistory 让 historyId 加 1、清空 history，之后比当前 historyId 旧的 startHistoryId 都返回 404，当前的 historyId 仍然有效，plugin 重新列一遍之后就能接着增量同步。
    • 写 mailbox.json 时先写临时文件再 rename。
